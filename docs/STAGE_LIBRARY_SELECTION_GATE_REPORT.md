## 5. Decision (§14, §15)

**SELECT_FLUENTMODBUS_5_3_2**

The host propagates `CancellationToken` (`SimulatorRuntime._loopCts` → `RunLoopAsync` → `Task.Delay`) and composes `IAsyncDisposable` stop/dispose. Both FluentModbus and NModbus expose `Task`-returning async reads, but only FluentModbus provides per-operation `CancellationToken` that integrates with this lifecycle without closing the socket; NModbus's `Task` async without a per-operation token cannot honor cooperative per-operation cancellation without external mechanisms (abandon `Task`, dispose/close transport, or rely on `ReadTimeout`). That per-operation token distinction is material, observed in the verified API signatures (`FluentModbus/Client/ModbusClientAsync.cs` with token vs `NModbus/Device/ModbusMaster.cs` without), and is not a generic benchmark preference. Corrected from earlier overstatement that NModbus is “entirely synchronous-only”: it does have `Task` async. NModbus's smaller footprint (0 vs 4 packages) and higher star count are noted but do not overcome the per-operation cancellation contract per the rule "do not select on preference/fewer deps/popularity alone". The #166 sequential gap is real but does not block the gated 1-Node `40`-word single-batch read (it is a 6-Node sequential scaling risk, deferred to bench measurement). No material blocker for FluentModbus was proven.

**Selecting:** FluentModbus 5.3.2 MIT `netstandard2.0` (verified compatible with `net10.0`), stable, pinned in CPM, read capability (explicit `TcRegisterArea` candidate `FC03`/`FC04` no fallback, `0`/`40` CANDIDATE_UNVERIFIED, raw `ushort[]` copied from transport-owned memory, configurable `IpAddress`/`Port`, `UnitIdentifier`, 125 PDU limit), per-operation `CancellationToken` + finite `ConnectTimeout=2000`/`ReadTimeout=2000`/`WriteTimeout=2000` (explicit `BigEndian` network order, CANDIDATE_UNVERIFIED, not cooperatively cancellable mid-Connect but bounded and fenced) + `IsConnected` + `Dispose` fenced by generation and one-outstanding gate, `ILogger` integration, loopback-testable, single-package server+client, infra-isolated behind `ITcReadOnlyClient`, no hardware verification, no `TEST_HARDWARE`/`PRODUCTION`, no write path.

**Rejecting:** NModbus 3.0.83 MIT `net6.0` (also `net10.0` compatible) — rejected for lack of per-operation `CancellationToken` on reads (exposes `Task<ushort[]> Read…Async` but without token; cooperative cancellation, deterministic shutdown and per-call timeout must be external — abandon `Task`, dispose/close, or rely on timeouts; lifecycle mismatch, not the mere existence of `Task` async), external `TcpClient` ownership (`master+tcp` double-dispose, `Retries` hidden-retry must be forced `0`), and linger issue #111. Zero-dependency footprint and larger community do not offset the per-operation token gap. Corrected from “sync-only” overstatement; the `Task` async without token distinction remains material.

Tie rule applied: tied without cancellation would have stayed FluentModbus (default) — here the cancellation contract breaks the tie materially.

Read-only limitation, `FC03` vs `FC04` unverified, address `0` unverified, `Unit ID` unverified, `40`-word contiguity unverified, signing/scaling (`0.1 °C/digit` Type K two's complement) unverified, wire-break/overrange unverified, 216-mapping unverified — all remain `CANDIDATE_UNVERIFIED`/`NOT_VERIFIED` until the next gate.
