## Context

WaterJet Sentinel Suite monitors 108 Sensors (I7 and I16 normal) with 216 assigned Front/Rear Thermocouple measurements out of 240 physical Channels (6 TC Nodes × 5 × 750-498 × 8, plus one 750-362 coupler and one 750-600 end module per Node, per `packages/commissioning/src/schedule.mjs` `PROTECTED_BASELINE` and `docs/evidence/tc-process-image-profile-rev1.md` DERIVED model-level map: 40 input words/Node at FC03/FC04 0–39, word-aligned, Intel format, analog-first). The approved TEST_CONFIGURATION addresses are `192.0.2.11–192.0.2.16` (canonical in `packages/commissioning/src/tcNodeConfiguration.mjs`, S2 exception), port 502 per the Owner-confirmed factory setting, and one WAGO 750-362 per Node. Physical reachability, FC03 vs FC04, start address, Unit ID, 40-word contiguity, word-to-channel correspondence, signedness/scaling (0.1 °C/digit Type K two's complement), wire-break (`0x7FFF`/`0x60` ambiguous with deactivated channel), overrange/underrange, 216-mapping and 24-spare identities all remain **NOT VERIFIED / CANDIDATE_UNVERIFIED** (see §2 of the task and `TC_EVIDENCE_SOURCE_REGISTER.md`). No ping, no probe, no TEST_HARDWARE, no PRODUCTION, no device write is authorized in this gate.

The previous leading decision was FluentModbus 5.3.2. The gate rule is: keep FluentModbus unless exact repository evidence or a controlled loopback spike proves a material blocker or that NModbus materially lowers risk. No custom Modbus stack, no third candidate, no hardware contact. This record corrects earlier overstatements that NModbus is “entirely synchronous-only”: NModbus does expose `Task`-returning async operations, but the verified per-operation `CancellationToken` distinction remains material (see §B, §C).

**Known defect affecting exact path:** FluentModbus issue #166 reports **~470–530 ms inter-request gap in sequential `ReadHoldingRegistersAsync` calls** even though the device replies in <60 ms. For a future 6-Node concurrent poll `Qty=40` single-batch per Node, the gap would still add ~500 ms per Node if reads were done sequentially; with bounded concurrency the total could stay ~500 ms (concurrent) but sequentially would be 6×500 ms = 3 s, exceeding the 1-second `HIS-003` acquisition interval. The defect is not triggered by a single 40-word read on one Node, but it is **material for the later six-Node scaling** and for any future sequential diagnostic reads. NModbus has no equivalent reported gap, but has its own linger issue #111.

**Finding C:** FluentModbus wins on **cancellation, timeout, and logging integration**; NModbus wins on **no-gap sequential reads**. The gap is material for the six-Node horizon, but the current gate is **one Node only** (next gate in §17), and the adapter's per-device serialization plus bounded concurrency (future) mitigates it. The gate rule says do not select on generic benchmark claims — the gap is a measured wire-level gap (60 ms vs 567 ms inside `ReadHoldingRegistersAsync`), thus a reproducible blocker for sequential use, but not a blocker for the single-batch one-Node foundation.

## Controlled Spike

A controlled spike was considered but **not required as a blocking step for the one-Node foundation**: the repository is `net10.0`, the `ITcReadOnlyClient` boundary was authored first, and the lifecycle properties (cancellation, timeout, stale fencing, disposal) are provable from the published API signatures and the adapter source itself (`FluentModbusTcClient.cs` shows generation fencing, per-call timeout restore, `OperationCanceledException` mapping, `ModbusException` mapping, and `IsConnected` gating). The spike rule allows local-only fake/loopback harnesses that bind only to `127.0.0.1` on an ephemeral port (never `0.0.0.0`, never `192.0.2.x`, never 502) — those harnesses remain available for the later One-Node Physical TC gate to obtain timing proof for #166 in the actual bench environment. No NModbus package was installed, no TCP socket was opened to any configured TC Node, no 502 contact occurred in Arena (verified via `grep` for `192.0.2` in Product tree — only the canonical config and the S2 exception contain them, and no `TcpClient.Connect` to that range exists).

If the later gate needs to quantify #166's impact on the 1-second interval with six concurrent clients, a bounded-concurrency loopback spike (`ModbusTcpServer` on `127.0.0.1:0` + six `ModbusTcpClient` instances) will be run Owner-local where `dotnet restore` can reach `nuget.org`. The losing candidate (NModbus) was never added to the graph, so no removal was needed beyond not adding it.

## Decision

**SELECT_FLUENTMODBUS_5_3_2**

Decisive evidence: for the WJSS host's `CancellationToken`-propagated lifecycle (`SimulatorRuntime._loopCts` pattern), **FluentModbus provides per-operation `ReadHoldingRegistersAsync`/`ReadInputRegistersAsync` with `CancellationToken`** (verified `ModbusClientAsync.cs`), while NModbus exposes `Task`-returning `ReadHoldingRegistersAsync`/`ReadInputRegistersAsync` **without** a per-operation `CancellationToken` (verified `NModbus/Device/ModbusMaster.cs`). The material difference is not the existence of a `Task` API — NModbus does have `Task` async — but the ability to request cooperative cancellation, deterministic shutdown, per-call timeout recovery and transport interruption per-operation via a token. NModbus's `Task` async without a token requires external mechanisms (abandon `Task`, dispose/close transport, rely on timeouts) and does not provide the same lifecycle fit as FluentModbus's token-aware reads. This lifecycle compatibility is material to the required “connect/read with cancellation, timeout, disconnect during outstanding operation, disposal, stale fencing” contract (§7) and to the boundary requirement that the adapter integrate cleanly with the runtime's `IAsyncDisposable` / `CancellationTokenSource` pattern. The transitive-dependency cost (4 packages, extra `PackageVersion` pins) is real but not a blocker, and the reported 500 ms sequential gap does not block the one-Node 40-word single-batch foundation (next gate will re-evaluate it under six-Node bounded concurrency with wire captures). No material repository-specific advantage of NModbus outweighs the per-operation cancellation contract. Do not claim NModbus is “entirely synchronous-only.”

**Reasons for selecting FluentModbus 5.3.2:**

- Compatible with `net10.0` (`netstandard2.0` computed compatible), MIT license, stable version 5.3.2, restored via CPM locked mode (pins verified Owner-local).
- Required read capability covered (FC03/FC04, start 0, qty 40, raw `ushort[]`, configurable host/port, unit identifier, 125-register PDU limit).
- Per-operation async with `CancellationToken` (`ReadHoldingRegistersAsync<T>(…, CancellationToken)` etc., verified), finite `ConnectTimeout`/`ReadTimeout`/`WriteTimeout` (bounded, not infinite), `IsConnected`, `Dispose` safely fenceable with generation counter; integrates with `ILogger` already used in `apps/runtime/Program.cs`. `Connect` itself is synchronous and not cooperatively cancellable mid-handshake, but is bounded by `ConnectTimeout` and fenced via generation on late success.
- Testable behind `ITcReadOnlyClient` with loopback `ModbusTcpServer` on ephemeral port, no production IP/port, no hardware claim.
- Single-package server+client for future commissioning tests.
- No hardware verification, no write path, no TEST_HARDWARE/PRODUCTION authority.

**Reasons for rejecting NModbus 3.0.83:**

- Lifecycle: exposes `Task`-returning `ReadHoldingRegistersAsync`/`ReadInputRegistersAsync` but **no per-operation `CancellationToken`** — cooperative cancellation, deterministic shutdown and per-call timeout recovery must be provided externally (e.g., abandon `Task`, dispose/close transport, rely on `ReadTimeout`/`Retries`), which does not match the host's per-operation `CancellationToken` contract and breaks the deterministic 1-second poll budget when cancellation is required mid-read. This is a material lifecycle mismatch for the WJSS runtime, not a preference. Do not claim `Task.Run` is mandatory or that `TcpClient.Close` is the only strategy unless the integration proves it.
- Requires external `TcpClient` ownership (master + tcp double-dispose ordering, `Retries` must be forced to 0 to avoid hidden retry that masks `COMMUNICATION_LOSS`), and the lingering-close issue #111 is a known operational risk for 24/7 SCADA use. These are separate verified concerns from the cancellation-token concern.
- Smaller footprint and larger community are noted but do not overcome the cancellation contract (per decision rule, do not select on “fewer dependencies” alone).

## Analyzer and lifecycle corrections (2026-10-13)

Owner-local targeted build `dotnet build adapters/tc-acquisition/Wjss.Adapters.TcAcquisition.csproj -c Release --no-restore` (SDK 10.0.401, correct PR head, `TargetPath`/`WJSS` overrides cleared) reached the adapter and failed with exactly three analyzer findings before any full build/test: **CA2263 at `FluentModbusTcClient.cs:206` (`Enum.IsDefined(typeof(TcRegisterArea),…)` → generic `Enum.IsDefined(request.RegisterArea)`), CA2016 at `:213` (`_singleRead.Wait(0)` without token → `Wait(0, CancellationToken.None)` preserving zero-wait fail-fast `READ_BUSY`), CA1513 at `:344` (`throw new ObjectDisposedException` → `ObjectDisposedException.ThrowIf(_disposed, this)`), plus a `SemaphoreSlim` disposal race (`ReadAsync` `finally Release()` vs `DisposeAsync` `Dispose()` could hide primary outcome).** Repaired (2026-10-13) with smallest safe changes: generic `Enum.IsDefined`, explicit `CancellationToken.None` (no queuing, no cancellable blocking), `ThrowIf` pattern (lock-protected, `this` identity), and removal of `_singleRead.Dispose()` (gate is managed admission state; not disposed, `Release()` always safe, no `catch` suppression, generation/transport/stale fencing preserved). `Wjss.Contracts` and `Wjss.Domain` compiled clean; full build/test not run after this failure; genuine lock remains untracked pending repaired-source regeneration. No change to warning policy (`TreatWarningsAsErrors` retained), no new test project (analyzer/behavior policy).
